## 1. 背景与依据（2026-09-29 spike 实测）

两轮实测（v1 压限额 + v2 常态 4.5h）确立的事实：

| # | 事实 | 数据 |
|---|---|---|
| F1 | 决策点 `OomAdjuster.updateAndTrimProcessLSP` 极高频 | 4.5h 34,700+ 次（≈2/s），reason 全谱正常，UI_VISIBILITY 32% 主导 |
| F2 | Oplus 免死闸门 `onHookKillCacheEmpty` 常态是**死路径** | 常态 6h **0 调用**；cached 池常态 10-18，远低于 cachedProcessLimit=100。压限额后可爆发 600 调用，放行率 34.6% 且放行对象全是 Oplus 自家应用 |
| F3 | 真实杀因全谱（A轨 killLocked 50 杀/4.5h） | Oplus强停 o-stop 32% / isolated 回收 32% / 用户划卡 16% / frozen-sync 14% / unlock 4% / excessive-cpu 2%；**cached#/empty# 超限杀为 0** |
| F4 | 白名单 3 应用（微信/QQ/抖音）轻度场景零死 | 两轮共 10h+，0 杀点 0 闸门 |
| F5 | `killLocked` 是 AMS 层全杀必经出口，reason 可判 | AOSP 标准点位，通吃 ROM（符合 lmkd 裁决方向） |
| F6 | `onHookKillCacheEmpty` 证明 AMS 容忍"决定不杀"分支 | 闸门 skipKill=true 时 killLocked 不被调用，进程保持注册，系统正常 |

结论：**B轨闸门不可作保活点位（F2），拦截点选 A轨 `killLocked`（F5），语义安全性有 F6 先例背书，杀循环是唯一系统性风险（F3 的 o-stop/force-stop 路径会重试）。**

## 2. 目标与非目标

**目标**：白名单应用在 AMS 层被系统性杀因（o-stop/frozen/CPU/超限）攻击时可拦截保活；拦截与被杀事件全程可归因；首版以观察模式上线，数据驱动放量。

**非目标（YAGNI）**：lmkd/内核层不归它管（COSMemory 阶段一已覆盖）；KILL/FREEZE 动作不进 hook 层；不做 per-app 差异化规则；不做图表下钻/筛选/导出/通知推送；不拦用户划卡；不救 isolated/unlock 期。

## 5. 配置桥协议（入向）

### 5.1 guard.conf 格式

由 COSMemory `service.sh` 生成到 `/data/system/cosmem/guard.conf`，权限 `0644 system:system`，格式继承名单 conf 风格：

```
# COSGuard bridge - generated by COSMemory service.sh
VERSION=1
MODE=observe                 # observe | guard   （首版出厂 observe）
BLOCK=o-stop,frozen,cached,empty,cpu
WHITE com.tencent.mm
WHITE com.tencent.mobileqq
WHITE com.ss.android.ugc.aweme
```

生成规则：
- `WHITE` 行 = 解析 `名单列表.conf` 的 WHITE 动作（复用 `engine/lists.sh parse_lists`），KILL/FREEZE **不进桥**（hook 层不关心）
- `MODE`/`BLOCK` 来源 = `config/memory.json` 新增字段 `guard: { mode, block_rules }`（缺省 `observe` + 默认集）
- 生成方式：写临时文件 + `mv` 原子替换；**生成失败保留旧文件**
- 文件缺失/VERSION 不符/解析失败 → hook 端 **fail-open：只记不拦**

### 5.2 BLOCK 规则名 → reason 匹配模式（内置映射，硬编码在 hook 端）

killLocked 的 reason 是自由文本，规则按子串/正则匹配（大写敏感、匹配 reason 字符串）：

| 规则名 | 匹配模式 | 对应 F3 杀因 |
|---|---|---|
| `o-stop` | 含 `due to o-stop` | Oplus 强停 32% |
| `frozen` | 含 `frozen`（Sync transaction while frozen） | frozen-sync 14% |
| `cached` | `^cached #` | 超限杀（常态 0，闸门管辖） |
| `empty` | `^empty #` | 超限杀（同上） |
| `cpu` | 含 `excessive cpu` | CPU 超限 2% |
| `killbg` | 含 `kill background` | **测试注入专用**（T4/T5 经 memory.json BLOCK 临时加入、测完还原）；**默认集不含**——am kill 属 shell 主动操作非系统强停，注入仅为实机构造保险丝重试环 |

- **默认 BLOCK 集 = 全部 5 个**；`remove task`（用户划卡）、`isolated not needed`、`unlockUserKey` **无规则名，永远无法被配进拦截**（D2 的"永不含划卡"用"不存在对应规则"实现，而非靠约定）
- 未知规则名：hook 解析时忽略该规则（不影响其余规则），并在下一次白名单事件时随行记 `RULE=config ACT=ERROR`；配置整体加载失败则独立追加 `TS|0|*|config|ERROR|<原因>` 行

### 5.3 热加载

hook 端每次事件前检查 `guard.conf` mtime，缓存 5 秒；变更即生效，**改配置无需重启 system_server**。首次加载失败进入 degraded（只记不拦），每 30 秒重试。

## 6. 拦截引擎（hook 端核心）

### 6.1 挂载（spike 已验证的模板直接复用）

- 入口：`onSystemServerStarting` 主 + `onPackageReady` 兜底，`AtomicBoolean` 幂等（v1.3/v2 实战通过）
- hook 点：`com.android.server.am.ProcessRecord.killLocked`，**全部 ≥5 参重载**（spike 观察到 String/int 双型重载，两者都是真实入口）
- `scope.list = system`；`exceptionMode=protective`；R8 keep 规则；包名 `com.xune.cosguard`
- 日志双写：`XposedInterface.log` + `android.util.Log.w`，tag `COSGuard`

### 6.2 决策链（顺序短路，任一步放行即 `chain.proceed()`）

```
on killLocked(reason, subReason, ...):
  1. tryLoadConfig()            # 5s 缓存+mtime热加载; 失败→degraded只记不拦
  2. pkg = pkgOf(app); if pkg ∉ WHITE: proceed   # 白名单外零开销直通, observe/guard
                                                  # 两模式下均不记(§6.3 "只记白名单相关")
  3. 事件级去重(T2勘误·前移): 键=pid|pkg|reason, 500ms窗
     命中 → record(PASS_DUP); proceed   # 一次杀跨多载重只记一次, observe 同样适用
  4. if MODE == observe:        record(PASS_OBSERVE); proceed   # 首版常态
  5. rule = matchFirst(reason)  # 按§5.2顺序匹配; 无命中: record(PASS_NO_RULE); proceed
  6. fuse = fuseMap[pid+":"+rule]
     if fuse.count >= 10:       # 保险丝: 连续拦满10次
         fuse.reset(); record(FUSE); proceed               # 放行1次让系统收敛
  7. fuse.count++
     record(BLOCK); return       # ★ skip: 不调 proceed, 进程不死
  catch (Throwable t):           record(ERROR); proceed     # fail-open 贯穿到底
```
- **pidOf 勘误（T2 实测）**：ProcessRecord 字段是 `public int mPid`（+`getPid()` 兜底），非 `pid`。

- **保险丝语义**：`fuseMap` 键=`pid:rule`；拦截成功不重置，放行后重置。10 次阈值 = 既容忍系统单次重试节奏，又保证 force-stop 类最多连续 10 次后必然收敛。`FUSE` 事件本身记遥测（WebUI 可见 = 杀循环的信号灯）
- **skip 语义安全性**：等价于 Oplus 闸门 `skipKill=true` 路径（F6），AMS 对"决定不杀"已有先例分支
- **记账幂等**：多重载互调时按 `pid+rule+reasonHash` 3 秒窗口去重，防止一次杀事件多计
- **红线**：`record()` 本身若抛异常，必须被外层 catch 吞掉并**仍然 proceed**——遥测永远不能成为拦截的理由或风险

### 6.3 遥测行格式（append，每次 open-append-close，无常驻 fd）

```
TS|PID|PKG|RULE|ACT|REASON
1790678523|12345|com.tencent.mm|o-stop|BLOCK|stop com.tencent.mm due to o-stop(40)
```
- `ACT ∈ BLOCK | PASS_OBSERVE | PASS_NO_RULE | PASS_DUP | FUSE | ERROR`
- **只记白名单相关事件**（第 3 步之后的判定才记；白名单外的直通不记）
- 文件：`/data/system/cosmem/guard.telemetry`，0644，单行 < 512B；无大小上限（service.sh 每轮收割）

### 6.4 收割（COSMemory service.sh）

```
[ -f guard.telemetry ] && mkdir -p data/guard && \
  cat guard.telemetry >> "data/guard/$(date +%F).log" && : > guard.telemetry
```
原子性：`cat >>` 后清空源；hook 端每次 open 新建/追加，被清空后下次 append 重建新内容，无竞态丢数据风险（单写者单读者、行级原子小写入）。

## 7. 统计与 WebUI「AMS防线」区块

### 7.1 engine/guard_stats.sh（新文件，统计全在 shell）

职责：聚合遥测归档 → 输出单个 JSON（前端零解析负担）。用 `ksu.exec` 调用，支持参数 `YYYY-MM-DD`（默认今天，含未收割的 live telemetry）。

输出 JSON 契约（**固定字段，spec 阶段定死**）：
```json
{
  "date": "2026-09-30", "mode": "observe", "module": "installed|absent", "live_today": true,
  "snapshot_age_s": 42, "fuse_threshold": 10,
  "today": {"block": 12, "fuse": 0, "error": 0, "pass_observe": 5},
  "hourly": [{"h": 0, "block": 0, "fuse": 0}, ...24],
  "rules": [{"rule": "o-stop", "n": 8}, {"rule": "frozen", "n": 4}, ...],
  "whitelist": [{"pkg": "com.tencent.mm", "name": "微信", "block": 6,
                 "last_ts": 1790678523, "last_act": "BLOCK"} , ...×3],
  "recent": [{"ts": 1790678523, "pkg": "com.tencent.mm", "rule": "o-stop",
              "act": "BLOCK", "reason": "stop ... o-stop(40)"} , ...10],
  "dates": ["2026-09-30", "2026-09-29"]
}
```
- `module` 由 `pm path com.xune.cosguard` 判定（installed/absent；"已装但未启用"不单独判定，改由 `live_today`=今日有无事件体现，无事件且 installed → 前端提示"检查 LSPosed 启用"）；`snapshot_age_s` = guard.conf mtime 距今（>3600 视为 stale，前端黄灯）
- `dates` = data/guard/ 下归档文件列表（供日期下拉）
- 无数据字段返回空数组而非省略（前端免判空分支）

### 7.2 WebUI 组件（5 个，封顶；纯 SVG 自绘，零外部库）

| # | 组件 | 形态 | 数据字段 |
|---|---|---|---|
| W1 | 状态总览卡 | 数字卡×4 + 状态灯 | `mode / module / live_today / snapshot_age_s / today` |
| W2 | 24h 拦截趋势 | SVG 柱状（24 根，BLOCK/FUSE 双色堆叠） | `hourly` |
| W3 | 规则命中分布 | 横向条形（规则名+计数+占比） | `rules` |
| W4 | 白名单应用卡片 ×3 | 卡片：图标/名称/今日拦截数/最近时刻/状态灯 | `whitelist` |
| W5 | 最近事件流 | 表格 10 行 + 日期下拉；行点击展开 reason 全文 | `recent / dates` |

约束：
- 纯 SVG/CSS 自绘（与现有 index.html 的 22 处 SVG 同路线），**不引入图表库**；新增体积预算 ≤ 20KB
- 交互只做 hover 提示与行展开；**不做**下钻、筛选、导出、推送
- 取数：页面进入/手动刷新时 `ksu.exec("sh engine/guard_stats.sh <date>")` → `JSON.parse` → 渲染；**不做轮询**（用户手动刷新即可）
- 样式融入现有单文件结构（class 前缀 `gd-`，不污染既有类名）

### 7.3 色义约定（与现有 UI 一致）

`BLOCK`=警示橙、`FUSE`=红（杀循环信号灯）、`ERROR`=红、`observe 模式`=蓝灰中性、状态灯 绿/黄(stale)/灰(absent)。

## 8. 安全与降级矩阵

| # | 场景 | 行为 | 验证用例 |
|---|---|---|---|
| S1 | guard.conf 缺失/损坏/VERSION 不符 | degraded：只记不拦，每 30s 重试加载 | T6 |
| S2 | WHITE 解析为空 | 同 S1（空名单=无可保对象，绝不等于全拦） | T6 |
| S3 | BLOCK 规则名未知 | 忽略该规则+记 ERROR，其余规则生效 | T5 |
| S4 | 杀循环（force-stop 重试） | 保险丝第 10 次放行并 reset，记 FUSE | T4 |
| S5 | hook/遥测内部异常 | 外层 catch → proceed + 记 ERROR（遥测失败永不拦截） | T5 |
| S6 | 模块自身崩溃 | `exceptionMode=protective` LSPosed 自动禁用，system_server 无感 | T9 |
| S7 | 用户划卡 | 无对应规则，**结构上不可拦** | T3 |
| S8 | 卸载 COSGuard | pm uninstall 即净，LSPosed 三表自动清零（spike 已验证） | T8 |
| S9 | 卸载 COSMemory | uninstall.sh 清 `/data/system/cosmem/` | T8 |

**红线汇总**：fail-open 贯穿（配置/解析/遥测任何失败都放行）；用户划卡结构不可拦；首版出厂 `MODE=observe`。

## 11. 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| skip 后 force-stop 路径状态不一致（F6 先例只覆盖 cached 杀分支） | 中 | T4 专项验证；保险丝保证收敛；observe 期无此风险 |
| ColorOS 升级改 killLocked 签名 | 低 | ≥5 参按数量匹配非签名匹配；C轨探针日志可快速发现 hook 失效 |
| 遥测文件被系统清理（/data/system 空间策略） | 低 | 每轮收割、量小；缺失不影响拦截 |
| WebUI 改动破坏现有面板 | 中 | class 前缀隔离 + 既有 tests/ 回归（§9.3） |
| 保险丝 10 次阈值不适配某场景 | 低 | FUSE 事件可观测（W1），阈值后续可配置化（本期硬编码） |

### 6.5 执行期勘误记录（2026-09-30 T2 实测回填）
